
## 架构结论与仍需观察的点

`daily.aggregate` 是按授权范围、时段、维度、指标、排序和分页工作的通用数据能力；规划与答复边界审查依据原请求和证据，不为“销量最差 ASIN”设置独立响应分支。不同问法已覆盖单期排序、两期变化、逐日明细、站点与店铺、权限范围、钉钉资源、公开数据和纯概念题。

当前仍有三个实际限制：

1. 底层跨站点业务数据完整性不足，部分榜单只能给出覆盖范围内结果，不能证明所有授权店铺的全量排名。
2. 紫鸟专用客户端/Bridge 尚未就绪，无法完成真实紫鸟店铺枚举。
3. 若干简单题调用了偏多的参考指南或相近数据能力；宽泛归因题也多次未通过完成校验，收敛慢。模型上游还出现过瞬时超时。应持续监测工具选择次数、完成校验拒绝次数、延迟、上游失败与恢复，不把单次答对等同于稳定性保证。

网关单元测试 169 项通过，TypeScript 构建通过；后端聚合与权限相关测试 14 项通过。网关与后端健康。验收结果只证明以上真实样本的行为，不代表任意未来问题都已穷尽验证。

## 追加验收：确认卡、个人文档与不同问法

随后修正了原会话原生确认卡的投递参数，并取消投递失败时展示普通文本“确认卡”的兜底：卡片投递失败会取消该项写操作，不等待文字确认。DWS 写入参数由当前安装版本的 leaf schema 提供，宿主在发出确认卡前拒绝不属于 schema 的参数；`--help` 不允许借业务写能力执行。网关 173 项测试及 TypeScript 构建通过。

使用原钉钉用户、原私聊入口真实创建了个人空间测试文档 `Agent验收沙盒 2026-09-27 S7K2`（任务 `896ee0b1-b71a-4c35-8b60-7650f5fe61b9`），再追加一行（任务 `c56a3536-56e2-4d8d-9f9e-7a56c08ea2aa`）。两次操作的原生确认卡均已创建；测试程序仅在卡片已投递、发起人/会话与原请求一致、审批尚有效、能力和参数与预期测试文档完全相符时，从原会话模拟该发起人的确认。生产确认门禁没有关闭。两项审批状态均为 `executed`，任务均为 `completed`。独立使用当前用户 DWS profile 读取文档，验证标题和正文、追加行确实持久存在。此前两次错误尝试已取消，未写入。

8 条追加回放使用原群请求的同一身份与授权，拦截对群投递以避免刷屏；8 条均结束为 `completed`，包括：指定日的单 ASIN 件数、最近 7 日零销量天数、上周零销量 ASIN、英国站各店铺件数、明确要求的两期对比、日本站授权店铺数、当天钉钉待办加日程、只用公开信号的搜索需求分析。单期与单日问题没有被强制改成环比。零销量 ASIN 题标为 `partial` 并说明 25 条不完整记录未计入，避免把缺失当 0；但用了 16 次数据调用，表明大范围枚举仍需更高效的服务端聚合或更严格的预算收敛。公开信号题未调用 CrossBorderOps，但用了较多 SIF 能力；后续应逐能力核实第三方 `ops`/`ads` 结果的公开性与可支持结论范围。今日待办题采用“今日到期”的能力，仍可能漏掉用户想看的逾期未完成事项，需进一步验证自然语言范围与能力覆盖是否一致。

这些回放覆盖读写、原会话投递、不同时间口径、跨能力查询、权限范围与来源边界；不构成任意提问均可正确处理的证明。尤其全量数据质量、宽范围查询时延及公开数据来源语义仍是生产验收项。

对“上周销量为 0 的 ASIN”的多次回放出现过 7 个与 58 条两个数。进一步检查后发现它们**不是同一统计粒度**：7 个是跨店铺汇总后的唯一 ASIN（65 个候选、43 个完整、22 个不完整），58 条是按店铺 × 站点 × ASIN 分组的零销量记录（160 条候选、135 条完整、25 条不完整）。因此不能把二者的差异直接归因于漏页，也不能把 58 条记录说成 58 个唯一 ASIN。此前把 7 个判为遗漏的结论已经撤回。实际根因是规划与完成校验没有固定用户所问对象的统计粒度，同一句话可能被执行成两种不同问题。

为此在任务契约中加入语义生成的 `enumeration`（完整集合、有限排名、单点、辅助事实）及 `grain`（统计对象维度）；独立规划审查核对它们是否忠实于原话。宿主对需要完整清单的分页结果计算同查询条件下 `total/offset/returned` 的连续覆盖，并比较返回的维度与契约 `grain`。这套机制作用于能力元数据及证据，不使用用户话语关键词路由。底层未入库或不完整的数据仍必须单独说明，分页完整不代表源数据完整。

## 2026-09-28 固定日期覆盖回归

使用原群任务的用户身份、授权与会话位置，真实调用模型和数据连接器，发送仍由回放器拦截以免刷群。六题固定为 2026-09-14 至 20，避免跨日运行使“上周”改变。测试文件为 `scripts/fixtures/coverage-regression.json`。

| 问题类型 | 最终真实回放结果 |
|---|---|
| 英国站每家授权店铺件数 | 两家有业务数据，分别 87、13 件；另两家授权店铺没有该期间可核实业务行，没有把缺失当成 0。 |
| 该期间销量为 0 的 ASIN | 7 个去重 ASIN；65 个候选中 22 个数据不完整，答复明确限制范围。 |
| 单个 ASIN、单日、日本站件数 | 0 件；没有加入无关比较。 |
| 当前可见日本站店铺数 | 8 家；只调授权范围能力。 |
| 单期销量前三 ASIN | 82、68、60 件；说明排名只覆盖数据完整的 ASIN，不加入跨期比较。 |
| 英国站销量合计 | 已记录业务行合计 100 件；点名两家授权英国店铺在该期间无源记录，不能说成全部授权店铺的确定总额。 |

回归中发现，业务聚合的 `coverage` 仅针对**已观测候选**，不能证明所有授权店铺均有可核实业务行。最初“英国站合计”只回答 100 件，遗漏了授权范围中两家无源记录店铺；给宿主增加硬拒绝后，模型重复查相近能力，8 分钟仍未结束。随后曾尝试让宿主把覆盖缺口强制标成内部 `partial`；这虽能拦住错误断言，却将某一类业务完整性判断泛化成全任务状态，容易限制其他问题的合理解法。**该强制改写现已撤回。**

目前将聚合工具的总体语义放在能力描述与结构化结果 `population_provenance`：当前用户权限过滤、仅已观测业务构成参与结果、`coverage` 只衡量已观测候选、未出现业务行的授权对象状态未知且不能推断为零。宿主可按任务哈希核对授权对象与同查询条件的业务行，并将差异作为审查证据；**不自动改变 Agent 的完成状态，也不生成固定答复**。独立审查单独核对答案实际声称的统计总体：若缺少授权全集与逐对象覆盖证据，不能把已观测聚合说成所有授权店铺的确定总额。模型可以自行决定查授权范围，或准确回答“已记录数据的合计”。不同探索查询按 `groupKey` 对齐，不能相互补足覆盖。

撤回强制状态后，真实回放的英国站合计在一次越界回答被审查拦下后，最终以模型自行生成的“已观测业务记录合计 100 件”完成，内部状态为 `answered`。单个 ASIN 单日 0 件及单期前三 ASIN（82、68、60 件）也再次真实回放通过，均明确来源范围而未加入跨期比较。网关 187 项测试与 TypeScript 构建通过，网关已重建重启。后端聚合服务同样加入 `population_provenance`；本机后端测试因缺少 `database.models.sif_keywords` 依赖，未能完成收集，运行中网关的适配层已向 Agent 提供相同字段。

仍需继续优化的是简单聚合题的成本：上述英国站合计在成功回放中经历数次独立审查拒绝，虽然最终收敛，但还不是稳定的低延迟体验。现有数据源无法为无业务行的店铺证明真实零销量，因此这些问题只能在当前证据下报告已核实部分。
