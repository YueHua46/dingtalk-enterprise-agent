## 审查为何能拖十几分钟

src/evidence-reviewer.ts 共用模型请求的默认 20 分钟重试预算、最多 6 次尝试，每次默认 180 秒，完整读取响应体也计入该次超时。首轮日志实际出现连续 4 次 AbortError，再第 5 次成功。因此“上游返回过 200”不代表响应体已成功完成。

首轮成功请求记录 58970 input tokens，请求体 192481 字符；第二轮约 56815 input tokens。主执行模型后续请求体增长至约 50 万字符。字符数不是 token 数，也不是上下文超限的证明。现有日志未证实 context_length_exceeded 或同类错误。

src/task-orchestrator.ts 将普通任务时间预算与模型重试预算相加，默认 15+20=35 分钟。本次路由记录 deadlineAt=2026-10-15T04:14:12.225Z，与该计算一致。系统目前容许一项任务接近 35 分钟才收尾。

此外，模型尚未生成用户要求的文件就结束回合，宿主直接把内部准备性答复送入完整模型审查，之后再要求修复。这浪费了可以用确定性“核心交付物缺失”检查提前发现的问题所占用的审查时间。

## PDF 失败的具体证据

1. 第一次 render_report 提交不符合 suffix 约束的货币后缀；该字段只接受百分号或空值，币种应在报告文字中呈现。
2. 第二次触发 REPORT_LITERAL_FACT_REQUIRES_BINDING：正文中的数量等数字尚未满足宿主事实绑定规则。
3. 保存的 payload.json 包含 84 个绑定；st1_term、st1_spend、st1_clicks、st1_orders、st1_impr 都仅按 sid=240 和同一 customer_search_term 选择 data.rows。只读重放匹配结果均为 3 行，不能唯一定位。事实解析拒绝是必要的数据保护；不得随便取第一行消除错误。
4. payload_fixed2.json 的行选择已能唯一匹配，但仍有 s240_acos、s7232_acos、s7240_acos、asin_top1_clicks 四个未使用绑定。后续 filtered_bindings.json 包含 80 个绑定。
5. 实际工具失败还包括 FACT_REFERENCE_UNUSED、REPORT_REVISION_NO_CHANGE，以及仅剩 FACT_RESOLUTION_FAILED 而无具体原因的反馈。完整性不足的错误使修复难以收敛。400 字符摘要确实截掉过 traceback 末尾，但渲染工具本身返回完整 reason；不能据此断言模型每次都只看到了 400 字符。

模型随后转向编写内部调试脚本，并用调试说明结束回合。再次进行业务交付审查时自然仍缺用户要求的报告，形成“未完成答复 → 耗时审查 → 修复失败 → 未完成答复”的循环。三轮后将审查失败原因作为 partial 结果结束，没有业务 PDF。

## 应修复的范围

- 在昂贵内容审查前加入确定性交付物检查：明确要求 PDF 却没有成功编译的文件时，直接给出一次可执行修复反馈；内容审查仍须对最终文件和事实执行。
- 独立审查使用独立的总耗时和重试上限；避免把每一轮审查都当作可以再占用 20 分钟的请求。超时后必须明确报告未完成核验，不能跳过核验发送文件。
- 报告编译返回结构化错误，列出事实 ID、匹配行数、候选维度、未使用 ID 和超时状态；避免无原因错误或长 traceback 隐藏关键问题。
- 修复循环以实际错误变化和剩余预算收敛；同一错误或无变化修订不得继续无限扩写脚本和上下文。
- 卡片明确区分排队、取数、编译、审查、修复和业务未完成；completed 与工作流 partial 的差别应向用户如实呈现。
- 同用户并发是独立设计问题。当前按 corpId:userId 串行，不能通过全局并发 30 推断同用户可同时运行 30 个任务；调整需要保留身份、记忆、写入和取消隔离。

## 已完成的代码修复与重放

- 发现并实际复现：80 个合法事实绑定的 Python stdout 为 610164 字节，超过 worker 的 execFile maxBuffer=512*1024。原错误 stderr 为空，宿主只反馈 FACT_RESOLUTION_FAILED。512 KB 限制下约 70 ms 失败，1 MB 下约 63 ms 成功。问题与模型上下文窗口不同。
- 实现共享对象引用的无损传输：同一份原任务数据从 610164 降至 86974 字节，512 KB 下成功；解码后 80 项与原始完整事实深度相等，保留查询、行维度、上下文、血缘。没有删除来源或放松唯一行约束。
- worker 空 stderr 时保留系统错误 code/message；事实解析区分超时和退出码；未使用绑定直接列出 ID。
- 失败草稿允许未改内容重试，已成功编译的同内容修订仍拒绝；answered 且存在未编译草稿时，宿主先阻断，避免再次启动昂贵语义审核。partial/blocked 仍可如实退出。
- 审核请求独立默认预算改为最多 2 次、共 360000 ms，每次 180000 ms；不再继承执行器的 6 次/20 分钟。显式配置原大预算仍生效。此上限是单次 review 的预算，并非整个任务累计审核预算。
- 审核事实来源无损共享：实际 verifiedFacts 从 119203 降至 62517 字符，并让 11 份证据摘录恢复为 16 份；总请求仅从 283947 降至 278218 字符，因为腾出空间被用于恢复证据。不能宣称整个审核请求减半。
- 模型代理补充响应结构诊断：输出类型、消息 phase、完成状态与 token 使用，不记录业务正文或凭据，不把普通文本转换为工具执行。

## 尚未解决的结构性问题

1. 首次没有登记计划、也没有创建草稿时，当前新增草稿门禁无法发现缺失 PDF。需要语义生成的明确交付契约（文件类型、数量、交付方式）及宿主按真实产物验收；不能从用户文本用关键词猜测。
2. 单次审核预算已独立，但多次审核仍能累计较长耗时；整个任务仍有原 35 分钟上限。应统一取数、编译、审核的累计预算和阶段进度，保留真正失败原因。
3. 同用户多会话仍被 corpId:userId 锁串行。需要按会话分离可并发只读执行，并逐项确认 memory/profile/写操作/取消隔离，再修改锁粒度。
4. 中转普通文本工具调用的起因尚缺转换前原生协议证据。不能把新增诊断日志说成已修复中转。
