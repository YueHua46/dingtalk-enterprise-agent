# 模块 8：对话修订、版本保存与对比

`ListingRevisionService` 提供 initialize、revise、read，消费模块 1/2/3/5/6/7 的宿主任务快照。运营在对话中说“只改标题”“第二点简短一点”“补回订阅费用”等即可；模块 10 的对话工具适配器会整理指令、目标字段和当前版本。此模块先实现业务服务，不要求运营填写标准表单，不增加审核人、审批按钮或审核状态，也不修改 Amazon 后台。

## 修订方式

- 模型修订：指令、上一稿、指定字段、检查问题和完整受控表达都作为数据送入统一模型接口。生成仍不注册业务工具，旧稿和指令不构成新增功能的依据。程序只合并指定字段；模型改了其他字段时，保留这些字段原文。
- 手动修订：宿主可提交带声明范围和出处的字段内容，不调用模型。目标支持 title、description、searchTerms、全部 bullets 或单条 bullets.N。N 为从 0 开始的内部索引，运营对话中的“第二点”须由适配器映射为 bullets.1。
- 每次修订都重新校验完整有效稿，不复用旧检查结论。改成 4K、免费订阅、丢失限定条件或无出处内容，仍会被模块 7 拦截。结构合法但内容有硬错误的修订可以保留为 blocked 版本供对比；其字段不能进入最终复制区。
- 产品信息变化时，宿主先重新准备来源、事实和规划。相同来源 ID/类型、属性、完整原值、原文片段和 trust 均未改变的事实，才允许将旧 ID 重新绑定到新出处；数值、条件或来源信任变化不自动重绑定。缺少新依据的旧声明会显式失效，不能静默改数字或拿新事实替旧承诺背书。

模型结果只是候选。最终版本记录的是程序合并后的 effective draft 和其完整新检查结果；generationReceipt 另保存未校验的模型回执，报告和 Excel 不应从回执中的未选字段取文案。模型核实项变化不会清除确定性检查问题。

## 版本与差异

每版记录父版本、顺序号、时间、修订类型/原因、来源/事实/规划/规则/校验策略快照、文案、检查结果及模型回执。版本 SHA-256 绑定整份快照；读取及幂等回执复用时检查摘要，不能给修改过的内容套旧版本。

差异逐字段保存前后文本、出处是否变化及按 Unicode code point 计算的增删片段，还记录资料/规划/规则/校验策略变化、核实项变化和检查问题增减。事实 ID 更新而文字未改，也有出处差异。恢复旧文案采用新修订版本，再次校验，不删除中间历史或复用旧通过状态。

scope 必须由宿主绑定当前 corpId/userId、原会话和 Listing 会话根 requestId，不由模型提供。群聊和私聊原文不能自动迁移。后续同一 Listing 的对话继续使用根会话标识；当前消息的身份、资源权限和资料读取仍由宿主按当前用户验证。

## 持久化、幂等与并发

`PgListingRevisionStore` 与迁移 `012_listing_revisions.sql` 保存当前指针、不可覆盖的版本和操作回执。每条 SQL 都包含用户、会话和会话根任务。JSON 使用 TEXT 保存，避免 JSONB 重排属性导致模块 6/7 摘要变化。Memory adapter 仅供测试和本地回放。

operationId 是宿主内部幂等键，不要求运营复制编号。相同键和相同请求复用回执；参数变化返回 idempotency_conflict。正在进行的相同操作返回 revision_pending，不重复调用模型。取消、超时、格式错误的已记录操作不自动重试；明确的新修订使用新键。

事务只覆盖操作登记和最后提交，不持有数据库锁等待模型。提交时再次检查 head 与基准版本：新的修订先完成后，迟到模型结果返回 stale_version，不能覆盖它。服务中断留下的 pending 操作不会自动重新生成，未知结果的判断与任务恢复由模块 10 接入宿主机制。当前服务也不设置审批或外部写入确认流程。

运行预算放在 config/listing-revision.json：指令、幂等键、补丁和版本存储大小。取消/生成失败保留旧 head；成功持久化后数据库已保存的草稿不是外部发布行为。数据库连接失败的未知提交结果须查询幂等回执，不能凭异常自动创建第二个操作。
