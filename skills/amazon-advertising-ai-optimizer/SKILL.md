# Amazon 广告分析方法

本 Skill 是通用分析方法和能力选择指南，不按站点启动固定流程。站点、币种和时区只用于查询范围与数据口径；美国、日本、德国及其他站点都使用同一套分析骨架。

## 通用工作流

1. **识别意图。** 判断用户是在看整体表现、找异常对象、分析搜索词、调整预算/竞价、判断利润、复盘优化，还是需要策略规划。
2. **确认范围。** 使用用户给出的站点、店铺、ASIN/SKU、广告类型、时间窗和目标。缺少不会改变结论的字段时采用合理默认值，并说明假设。
3. **选择最小能力。** 只读取能回答问题的数据。整体表现优先汇总；活动/广告组问题下钻活动数据；搜索词问题读取搜索词；广告位问题读取 placement；利润问题补成本费用；库存或 Listing 原因再读取对应业务数据。
4. **读取方法资料。** 基础方法使用本 Skill 和通用经营分析 Skill。只有当前问题需要时才读取专项 Skill 或站点经验包。经验资料不能代替实时业务数据。
5. **取证和计算。** 内部店铺数据优先使用当前用户范围内的 CrossBorderOps；缺字段时使用经过范围校验的领星只读能力或用户提供的报表。派生指标使用 analysis.table 或 analysis.python，分母为零和缺失字段保持未知。
6. **分析和表达。** 区分数据事实、计算结果、经验参考、高可信推断、待验证假设和无法判断。相关性不能直接写成因果。
7. **选择交付。** 默认在聊天中简洁回答。只有用户明确要求 PDF、导出或下载时才生成文件；PDF 只包含本次问题需要的章节，不自动套用完整长报告。

## 意图到能力的映射

- 整体广告表现：广告汇总、活动或产品层指标。
- 高花费低转化对象：活动、广告组、投放目标或关键词报告。
- 否定词和搜索词治理：客户搜索词报告，必要时组合搜索词分析 Skill。
- 预算和竞价建议：广告指标 + 业务目标 + 利润/库存约束。
- 盈利和保本判断：实际成交价、成本、佣金、履约、退款和目标利润。
- 优化后复盘：两个可比窗口、历史调整记录和归因成熟度。
- 库存或 Listing 影响：库存、销售、Listing、价格、促销和广告数据。
- 策略规划：通用广告策略 Skill 作为方法参考，账户事实仍必须来自当前任务证据。

## 站点经验包

站点经验是可选参考，不是平台官方规则、默认阈值或 Workflow 分支。使用前检查站点、产品、广告类型、阶段、目标和样本条件；条件不满足时只作为背景，不能直接触发动作。

- 美国站：references/usa-profit-model.md、references/source-us.md
  - 主要参考利润、CPA/CPC、阶段策略和库存约束。
  - 价格、成本和参数必须来自当前 ASIN；文档中的示例价格不能当默认值。
- 日本站：references/japan-rules.md、references/source-jp.md
  - 主要参考新品/成熟期、搜索词观察和预算分层。
  - 阈值属于运营经验，不能替代当前数据、产品阶段和目标。
- 德国站：references/germany-rules.md、references/source-de.md
  - 主要参考高客单价产品的样本门槛、冷却期、加购和德语搜索词。
  - 只有产品和数据条件得到核验时才引用；不能将经验阈值泛化到其他品类或站点。

没有对应经验包的英国、加拿大、意大利或其他站点，继续使用通用方法完成分析，不因缺少站点文档而阻塞。

## 来源与权限

- 所有内部查询使用当前任务的 corpId + userId 和宿主计算的有效店铺范围。
- CrossBorderOps 是首选内部来源；领星只读能力只能在范围校验后补充使用。
- 共享 lingxing.action 保持禁用。
- Amazon 公开页面、SIF 和知识库不能替代内部广告报表，除非用户明确要求公开市场信号。
- 站点经验、开源 Skill 和官方资料必须标明来源性质，不能把经验写成官方要求。
- 预算、竞价、否定词、状态和活动结构只生成建议；真实写入仍需宿主确认。

## 运营核验与原因诊断

- **保留 AI 的运营判断。** 广告分析不是只把指标代入固定公式；模型应结合当前数据、通用广告方法和适用经验给出评价、优先级、原因解释与行动建议。宿主需要硬性核对的是判断所引用的对象、日期、范围、指标和计算结果准确，不能因为结论带有主观判断就把分析降级成数据罗列。正文把内容分成“数据事实”“AI 评价/推断”“建议动作”“待验证前提”，让运营知道哪些是报表直接显示、哪些是模型判断。

- 来源按每条实际证据确定，可能来自任意已授权系统、公开资料或用户文件；来源优先级不等于已使用来源。只查询了 CrossBorderOps 就不能写成直接取自领星，编号映射也不能证明上游采集来源。对运营展示可以使用已确认的友好名称，例如“CrossBorderOps · 运营后台”；内部仍保留真实提供方。系统/材料名称无法确认时如实标为待核实。
- 面向运营使用业务名称解释实际报表、日期、站点、店铺和对象、必要筛选条件、计算口径；各项分行或分块呈现，共用来源编号，不堆成长段落。原始数据库/API字段及技术参数只留内部审计。没有证据的后台菜单、负责人或报表链接不能猜测。
- 客户实际搜索词使用 `customer_search_term`；`keyword_text` 是配置的关键词或投放表达式，不能混用或用“搜索词/投放词”标签掩盖口径。建议否定实际搜索词前先核验该字段、活动/广告组及匹配类型。已有订单或销售的对象称高花费低转化，不称零产出/空耗。
- 数据水位、上游完整性与平台归因窗口分别解释。报表未给出归因窗口时明确未知，不能凭通用印象写固定天数；引用具体平台窗口须有本任务查得的适用官方来源。覆盖仅为已入库 SP/SB 搜索词数据时，正文和聊天都说明该范围，不能仅在机器字段中写 not_verified，正文却称全账户完整覆盖。
- PDF 的来源编号与核验附录由宿主根据 fact_bindings、表格 source 及计算血缘自动生成。仍需在正文交代业务口径，尤其是对比窗口、币种、SP/SB 等互斥来源、归因窗口和采集完整性；不能仅写“后台数据”作为出处。
- 用户要求跨期比较时，交付物需保留两个期间的关键观测及其来源，不能只展示本期表格并用“恶化/飙升”替代比较。分母为零的期间比率不可比较为涨跌。正文中的诊断和范围说明也用短段或分项，不把多项缺口合并成大段免责声明。
- 复杂诊断先按用户目标与影响规模筛选少量优先对象，再按证据需要下钻搜索词、投放、广告位、产品、库存或 Listing；不把所有能力调用一遍当成分析。对比采用可比窗口和加权比率，不平均 ACOS、不混加币种、不重复加总重叠报表。
- 区分“效率较差/恶化”“未转化样本”“已亏损”：没有实际成本或目标约束，不能把高 ACOS 直接判为亏损；零订单和短样本不能证明应立即停投。
- 原因分为已观测机制、证据支持的解释和待验证假设。例如先用 CPC、CTR、CVR 及流量结构分解差距；没有竞价/预算配置、历史调整、库存或 Listing 证据时，不断言出价过高、预算不足、缺货或页面问题。
- 广告归因销售额除以订单数只能说明该样本的平均每单归因销售额，不能单独证明商品售价、市场定位或“低客单产品”；称高低还需要可比基准。可解释效率指标的数学变化，但不能据此断言产品属性或根因。报表没有可验证时区时写待核实，不凭站点推定具体业务日时区。
- 判断搜索词是否“不相关”及建议精准否定，必须有对应广告商品、ASIN/Listing 或用户明确的产品定位作为前提。不能从活动名中的 solar、system、camera 等词推断产品是单机还是套装；转化低只证明该样本表现，不能证明需求错配。缺少产品证据时，将相关性与否定动作列为待核验条件，优先提出核查与有限试验，不直接给出必然应否定的结论。
- 行动中的前提必须约束行动本身：尚待核查时写“若核实……再考虑……”，而不是先要求下调/否定、再在备注中补一个待验证条件。只要求分析时，建议与观察窗口可提出，但不能暗示已执行或保证收益。对比诊断按证据选用 CPC、CVR、CTR、客单价和流量结构解释，不用通用动作清单代替本次原因分析。
- 人员归属只使用授权范围内明确的店铺/广告负责人与有效期绑定。没有对应字段时按店铺/活动完成分析并说明人员维度缺口，不将访问权限当作运营责任或绩效归因。

## 默认输出

简短聊天回答按以下顺序组织：

1. 结论。
2. 范围与口径。
3. 关键证据。
4. 1–3 项优先行动。
5. 数据缺口或待验证项。

简单指标问题只回答该指标和口径；不要因为加载了广告 Skill 就生成完整诊断。用户明确要求 PDF 时，登记 delivery.format=pdf 并读取通用 PDF Skill，使用 artifact.render_document 自由选择与排列本次问题需要的内容块。HTML/CSS 主题只统一字体、颜色、间距和分页，不规定业务章节或封面。正文事实用 fact_bindings，表格和按需使用的图表用 source 绑定证据；检查实际 PDF 页面预览后用 artifact.submit 交付。广告 PDF 只有这一条新建和修订路径，不存在旧模板回退。
